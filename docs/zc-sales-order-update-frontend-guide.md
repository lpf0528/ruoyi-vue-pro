# 销售订单整单更新接口——前端对接改造说明

> 本文档描述后端对整单更新接口的改造内容，前端需按照以下规则调整提交逻辑。

---

## 一、涉及接口

| 接口 | 说明 |
|------|------|
| `PUT /zc/sales-order/update` | 成品订单整单更新 |
| `PUT /zc/sales-order/fabric/update` | 面单整单更新 |

其余接口（确认、完成、裁剪等）**不受本次改造影响**。

---

## 二、核心变化：子表行需要回传 `id`

### 背景

旧版本整单更新时，后端会先删除所有子表行再全量重建，导致行 ID 每次都变、已裁剪的配料状态丢失。

新版本改为 **三路 merge** 策略：
- 请求中携带 `id` 的行 → **UPDATE**（更新已有行，ID 不变）
- 请求中不携带 `id` 的行 → **INSERT**（新增行，后端生成 ID）
- 数据库中存在但请求中未包含的行 → **DELETE**（后端自动删除）

### 新增字段

以下嵌套层级均新增可选的 `id` 字段：

| 层级 | 字段路径 | 类型 | 说明 |
|------|---------|------|------|
| 成品订单 - 窗帘行 | `curtains[].id` | Long | 可选 |
| 成品订单 - 结构行 | `curtains[].structures[].id` | Long | 可选 |
| 成品订单 - 用料明细 | `curtains[].structures[].materials[].id` | Long | 可选 |
| 面单 - 窗帘行 | `curtains[].id` | Long | 可选 |
| 面单 - 结构行 | `curtains[].structures[].id` | Long | 可选 |

---

## 三、前端必须遵守的规则

### 规则 1：编辑已有行时必须携带原行 `id`

调用详情接口 `GET /zc/sales-order/detail` 时，每一层的行数据都包含 `id` 字段。前端在将详情回显到编辑表单时，需将这些 `id` 保存下来，提交更新时原样带回。

```json
// 示例：编辑已有窗帘行，id 必须回传
{
  "id": 1001,
  "curtains": [
    {
      "id": 2001,          // ← 回显时从详情接口取到的 id，必须带回
      "curtainId": 100,
      "room": "主卧",
      "structures": [
        {
          "id": 3001,      // ← 同上
          "structureId": 200,
          "materials": [
            {
              "id": 4001,  // ← 同上
              "productId": 300,
              "quantity": 5
            }
          ]
        }
      ]
    }
  ]
}
```

### 规则 2：新增行时不传 `id`（或传 `null`）

用户在表单中新增的行没有数据库 ID，提交时该字段留空或不传，后端识别为新增并生成新 ID。

```json
// 示例：新增一条窗帘行（无 id）
{
  "curtainId": 101,
  "room": "书房",
  "structures": [ ... ]
}
```

### 规则 3：删除行只需从请求体中移除

不需要调用单独的删除接口。提交时某行不出现在请求体中，后端会自动将其从数据库删除。

> ⚠️ **例外**：已裁剪的用料明细行**不允许删除**，见下方第四节。

---

## 四、已裁剪用料行的限制

### 背景

用料明细（`materials`）有 `status` 字段，表示配料状态：

| 值 | 含义 |
|----|------|
| `NOT_PEILIAO` | 未配料 |
| `HAVE_PEILIAO` | 已裁剪（库存已出库） |

已裁剪的行与库存扣减记录绑定，删除会导致账目不一致，后端会拦截。

### 前端限制

**① 禁止删除 `HAVE_PEILIAO` 行**

如果用户尝试在编辑表单中删除状态为 `HAVE_PEILIAO` 的用料明细行，前端应阻止操作并给出提示，例如：

> "该用料明细已完成裁剪，请先撤销裁剪后再删除"

建议直接在 UI 上禁用该行的删除按钮（`status === 'HAVE_PEILIAO'` 时隐藏或禁用删除图标）。

若前端未做拦截而直接提交，后端会返回错误：
```
错误码：100077
错误信息：存在已裁剪的用料明细，请先撤销裁剪后再保存订单
```

**② `HAVE_PEILIAO` 行的批次字段只读**

已裁剪行的 `batchId`（批次）字段即使前端修改后提交，后端也不会更新（保护库存绑定关系）。建议将已裁剪行的批次字段在 UI 上设为只读或禁用。

**③ 其他字段仍可修改**

已裁剪行的单价（`price`）、用量（`quantity`）、折扣率（`discountRate`）、小计（`amount`）等业务字段仍然可以修改并正常保存。

---

## 五、`mountings`（配件）字段行为变化

窗帘行的配件字段 `mountings` 由字符串数组提交。

| 提交值 | 旧版行为 | 新版行为 |
|--------|---------|---------|
| 非空数组 `["加铅块"]` | 正常保存 | 正常保存（不变） |
| 空数组 `[]` 或不传 | **不清空**，保留原值 | **清空为 null** ⚠️ |

> 新版本提交空数组或不传 `mountings` 时，后端会将该字段清空。如果业务上"不传"代表"不修改"，前端需确保编辑时始终将原值带回。

---

## 六、典型提交流程

```
1. 打开编辑弹窗
   └─ 调用 GET /zc/sales-order/detail?id=xxx
      └─ 将返回的 curtains[].id / structures[].id / materials[].id 存入表单状态

2. 用户编辑
   ├─ 修改已有行：字段改变，id 保持不变
   ├─ 新增行：id 为 null / 不填
   └─ 删除行：
       ├─ status = NOT_PEILIAO → 允许，从列表移除
       └─ status = HAVE_PEILIAO → 禁止，提示用户先撤销裁剪

3. 提交
   └─ 调用 PUT /zc/sales-order/update
      └─ 请求体中每个已有行携带原 id，新增行不带 id
```

---

## 七、不受本次改造影响的内容

- 创建接口（`POST /zc/sales-order/create`、`POST /zc/sales-order/fabric/create`）逻辑不变，子表无需传 `id`
- 确认、取消确认、完成、标记加急、裁剪、撤销裁剪等接口均不受影响
- 请求体中订单主表级别的字段（`customerId`、`amount`、`deliveryAddress` 等）无变化
